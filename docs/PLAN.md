# Components Swapper — план

Плагин Figma: дизайнеры собирают макеты из разных старых библиотек; плагин переводит макет на компоненты и иконки
WB AID Rider/Driver с сохранением контента, а дальше предлагает новые компоненты и доработки существующих.

## Ограничения платформы

1. **Plugin API не перечисляет компоненты библиотеки** (`teamLibrary` — только переменные). Индекс собирается плагином
   в открытом файле библиотеки и хранится вне макета.
2. `importComponentByKeyAsync` импортирует только опубликованные компоненты.
3. `documentAccess: dynamic-page` — главный компонент экземпляра читается только `getMainComponentAsync()`.
4. `swapComponent` переносит оверрайды по совпадению имён слоёв; вложенные instance swap и привязки переменных могут
   сброситься (правила 12, 15, 28 скилла) — переносим сами.
5. Ключ ИИ в плагине не спрятать — ИИ только через сервер.

## Архитектура

```
├─ config/libraries.json   ← библиотеки компонентов и иконок: id, продукт, вид, fileKey
├─ src/
│  ├─ core/                ← без Figma, покрыто тестами; движок замены — только отсюда
│  ├─ figma/               ← индекс библиотеки, скан, замена через Plugin API
│  ├─ shared/messages.ts   ← sandbox ↔ UI
│  └─ ui/                  ← Preact
├─ server/                 ← (позже) Worker: индексы, прокси ИИ, предложения
└─ tests/                  ← vitest
```

Сопоставление без ИИ: имя (нормализация + синонимы), структурный отпечаток поддерева, `detachedInfo` у отвязанных
фреймов, перцептивный хэш растра (UI-iframe, canvas). ИИ — только этапы 4–5 (имена, описания, обоснования) и спорные
случаи.

1. 🟡 **Замена по имени с сохранением контента (+ иконки).**
   - 🟡 1а–1б — отчёт и подбор (ждёт проверки в Figma): для каждого чужого и локального компонента — наш с тем же
     именем (`src/core/match.ts`: нормализация имени, продукт макета угадывается по числу пар, одноимённые
     разводятся размером ±20 % — правило 27); статусы «Пара / Другой размер / Выбрать / Нет пары»; выбор дизайнера
     в списке; примерка «Было / Будет» на временной копии (правило 31) с вариантом по осям (`src/core/variants.ts`,
     правило 28) и проверкой текстов (`src/core/content.ts`). Макет не меняется.
   - ⬜ 1в — применение с отменой: `swapComponent` по выбранным парам, проверка текстов до = после, вариант по осям;
     1г — второй проход: старые вложенные иконки внутри заменённых → наши по имени (спайк: `swapComponent` их оставляет).
   *Готово:* ≥95 % чужих экземпляров с аналогом по имени заменены, 0 потерянных видимых текстов (автопроверка),
   отмена возвращает экран; проверено инженером в Figma.
2. ⬜ **Структурное сопоставление.** `detachedInfo` → ручные фреймы с визуальными свойствами (правило 32); отпечаток
   поддерева + перцептивный хэш; точное — авто, частичное — с подтверждением, составное — поиск набора по вложенным
   ключам. *Готово:* точность автозамены ≥90 % на размеченном наборе, ни одной ложной автозамены.
3. ⬜ **Иконки по рисунку.** Подход Token Comparator (IoU 32×32, пороги 0.97 / 0.85) — как именно переиспользовать,
   решает PD. *Готово:* копии и отвязанные иконки находятся с похожестью ≥0.97, спорные — выбор дизайнера.
4. ⬜ **Повторы → новые компоненты.** Кластеры поддеревьев (≥3 экрана или ≥5 мест), различия → оси и свойства,
   черновик компонента на странице предложений с описанием и обоснованием. *Готово:* инженер согласен с ≥70 % топ-10.
5. ⬜ **Доработки наших компонентов.** Разница «наш ↔ похожий в макете» + чек-лист стандартов ДС, только с
   доказательством. Библиотеку плагин не меняет. *Готово:* первое предложение рассмотрено владельцем библиотеки.
